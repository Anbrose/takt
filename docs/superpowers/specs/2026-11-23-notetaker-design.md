# 录音笔记（Note taker）— 设计

日期：2026-11-23 · 状态：已确认（2026-11-24）

## 为什么做

规划常常发生在说话的时候：一场讨论、一次边走边说的构思。等到坐下来打开 TAKT，细节已经忘了一半。

录音笔记让用户**先把整段话录下来**，之后从里面**提取出一条或多条任务链**，再挑出需要的部分导入到某个 Project。录音和提取都不需要先想好「这属于哪个 Project」。

## 目标

1. **长录音**：一次可以录很久（目标：1–2 小时）。锁屏或切到别的 App 时继续录；App 被系统杀掉时最多丢失最后几秒。
2. **未认领**：录好的笔记不属于任何 Project，放在单独的「笔记」列表里，等以后再处理。
3. **手机上识别**：用 iOS 26 的 `SpeechTranscriber`，在设备上把录音转成带时间戳的文字稿。
4. **录音留存在 GCS**：原始录音上传到 Google Cloud Storage，以后需要时可以重听，或用更好的模型重新识别。
5. **提取任务链**：点「提取」按钮后，后端用大模型从文字稿里提取 **1 条或多条任务链**。每条链有 ≥1 步，每一步有名称，录音里提到地点时也带上地点。
6. **导入**：
   - 默认把一条链整体导入到用户选定的某一级：生成一个新任务（链名），链里的各步按顺序成为它的子任务。
   - 长度为 1 的链直接导入成一个普通任务，不包一层。
   - 链可以拆开：用户勾选其中几步，单独导入到别的 Project 或别的一级。

## 不做（这一轮）

- **iOS 26 以下的设备**。这个功能只在 iOS 26 及以上出现，App 的其他部分仍支持 iOS 17。
- **云端识别**（Google STT v2），以及「在云上重新识别」的按钮。数据结构为它留好位置（录音在 GCS，文字稿可以整体替换），但这一轮不接入。
- 边录边显示实时字幕。录完（或每录完一段）再识别即可。
- 网页端界面。
- 多用户、分享笔记。目前仍是单用户（`owner = local` 或 API token 对应的 owner）。
- AI 估算耗时和花费（这是 `task-time-cost` 设计里另外排期的项目）。
- 提取结果直接写进 Project。AI 只出草稿，一定要用户确认。

## 绝不能出现的情况

- **录音丢失**：任何时候（断网、App 被杀、上传失败），已经录下的内容都必须还在手机上，直到确认上传成功。
- **AI 直接改动用户的 Project**：导入只在用户点确认后发生。
- **提取出的任务看不出来自哪句话**：每一步都要能跳回文字稿里对应的位置，并从那里播放录音。
- **录音流经 API 服务**：Cloud Run 实例只有 512 MiB 内存、最多 1 个实例，录音必须由手机直接传到 GCS。
- **界面上多出说明文字**：遵守「尽量少文字」的准则，只显示关键值，比如时长 `1:12:05`、链数、步数。

## 约束

- **先画画布再写代码**：笔记列表、录音界面、笔记详情（文字稿 + 提取结果）、导入流程，都先在 Design 画布的 `Phone` / `PhoneDark` 画板上做出来，用户确认后再实现。
- 动效遵守 `design/guidelines.md`：每个过渡都要插值，不能在一帧之内跳变。
- 接口先在 `packages/contract` 里用 Zod 定义，再生成 `openapi.json` 和 Swift 客户端（与现有做法一致）。
- 基础设施放在悉尼：GCS bucket 在 `australia-southeast1`，和 Cloud Run、Neon `takt` 一起。属于 Pigdogie 名下的 GCP 项目。大模型调用例外，可以用其他区域。
- 发给大模型的只有文字稿，不发录音。
- 后端在没有 GCP 凭据时（本地开发和测试）也要能跑：存储和大模型都要能换成本地/假的实现。

## 考虑过的做法

| 做法 | 内容 | 取舍 |
|---|---|---|
| **A. 手机识别 + 后端提取（选用）** | 手机录音并识别；录音分段续传到 GCS；文字稿存后端；「提取」时 Cloud Run 调用 Vertex AI 上的大模型 | 识别免费、离线可用；后端只多一次同步调用，不需要任务队列；文字稿带时间戳，方便核对。代价：长录音在手机上识别的耗电和发热需要真机实测 |
| B. 全部放在云上 | 录音上传后由后端调用 Google STT v2 批量识别，再提取 | 手机不费电。代价：按分钟收费、有延迟；要搭异步任务和状态轮询；悉尼区域可用性未确认 |
| C. 录音直接交给多模态大模型 | 一次调用完成识别和提取 | 流程最短。代价：拿不到可靠的带时间戳文字稿，没法核对；长录音费用高；换模型不方便 |

**选 A 的原因**：成本最低、后端最简单，而且数据结构和 B 一样。真机测下来手机识别撑不住时，只需要把「识别」这一步换成 B，存储、文字稿、提取、导入都不变。

## 已经定下的做法

### 离线优先

- **没网也能开始录音**：笔记 id 由手机生成（UUID），`POST /notes` 接受客户端给的 id，重复提交同一个 id 视为成功（幂等）。
- 笔记、各段录音、文字稿先存在手机本地，有网时由同步队列依次完成：建笔记 → 写文字稿 → 上传各段。App 重启后队列继续。
- 「提取」和「导入」需要联网，没网时按钮不可用。

### 说话人区分（先做技术验证）

- `SpeechTranscriber` 本身不区分说话人。用开源的 **FluidAudio**（Core ML，MIT/Apache 2.0）在手机上做说话人区分，再按时间重合把每段文字归给说话人。
- **技术验证结果（2026-11-23，Mac M1 Pro，合成的三人中文对话 51 秒）**：
  - 用离线管线 `OfflineDiarizerManager`：8 句话、3 个说话人**全部分对**，处理 51 秒录音约 0.6–2 秒。
  - `SpeechTranscriber` 的结果每段约 12 秒，会跨说话人，**不能按段归属**；要用每个词的 `audioTimeRange`（`attributeOptions: [.audioTimeRange]`）逐词归给时间重合最多的说话人，再把相邻同一人的词合并成一句。这样做 8 句全部归对。
  - 体积：说话人模型约 21 MB（首次使用时下载，或随 App 打包）；FluidAudio 全量编进去约 22 MB，另有一个 94 MB 的文本处理依赖（TTS 用），用 SwiftPM trait 只启用 `Diarizer` 可以去掉，但验证时链接失败，留给实现者处理。
  - **识别准确度是更大的风险**：合成语音上，日本地名几乎全错（伏见稻荷大社 → 福建造合照社），`AnalysisContext` 的提示词对 `SpeechTranscriber` 没有效果。需要用真人录音再测；提取时让大模型结合上下文纠正地名，再经地点联想确认。
- 结论：纳入这一轮。
- 不管做不做，文字稿每段都留一个可空的 `speaker` 字段；笔记上存说话人名单（默认「1」「2」…，用户可改名）。提取时把说话人一起交给大模型，帮助分清「谁负责做什么」。

### 数据

新增一张 `notes` 表（**不**放进隐藏的收件箱 Project——没导入前它们不是任务，放进任务树会让现有的列表、地图、排序都要先把它们过滤掉）：

| 字段 | 含义 |
|---|---|
| `id`, `owner_id`, `created_at` | 同其他表；所有查询按 owner 过滤 |
| `title` | 默认是录音开始的时刻，用户可以改 |
| `locale` | 识别语言，例如 `zh_CN`、`ja_JP` |
| `duration_ms` | 录音总时长 |
| `audio` | 录音在 GCS 里的位置（见下方「录音存储」），以及上传状态 |
| `transcript` | 文字稿：片段数组，每段有 `startMs`、`endMs`、`text`、`speaker?`；整体存成 JSON |
| `speakers` | 说话人名单（id → 名称），没有区分说话人时为空 |
| `transcript_source` | 识别来源，这一轮固定为 `device`（以后可以是 `google-stt` 等） |
| `extraction` | 最近一次提取结果（任务链草稿），整体存成 JSON；没提取过为空 |

任务链草稿的形状：

```
chains: [
  {
    id,                 // 草稿内的 id，导入时用来指明选了哪些
    name,               // 链名，例如「京都一日游」
    steps: [
      { id, name, place?, quote: { startMs, endMs } }   // quote 指回文字稿
    ]
  }
]
```

每一步记录**导入状态**（未导入 / 已导入到哪个任务），这样一条链拆开导入几次后，用户看得出哪些还没处理。所有步都导入后，笔记在列表里显示为已处理（是否自动归档见「留给实现者」）。

### 录音（iOS）

- 用 `AVAudioRecorder` 或 `AVAudioEngine` 录成 AAC（`.m4a`，单声道，适合语音的码率），**按固定时长切段**（例如每 5 分钟一个文件）。切段的好处：
  - App 被杀时只丢最后一段未写完的部分；
  - 每段录完就能开始上传和识别，不用等整场结束。
- 打开后台音频（`UIBackgroundModes: audio`），锁屏和切出时继续录。处理来电等音频中断：中断时暂停，结束后自动继续。
- 录音中的界面只显示时长和一个停止按钮。

### 识别（iOS 26，`SpeechTranscriber`）

- 每段录完后在设备上识别该段文件，结果按段的起始偏移换算成整场录音的时间戳，拼进文字稿。
- **录音前选语言**（已确认）：一段录音只用一种语言识别（`SpeechTranscriber` 不会自动判断语言，也不能中途切换；整句换成别的语言的话那部分会被丢掉，验证里整句日语完全没有出字）。用户不会在一段对话里整句切换语言，所以：
  - 录音按钮旁边有一个语言选择，默认是上次用的语言（第一次是系统语言），可选列表来自 `SpeechTranscriber.supportedLocales`（45 种，含普通话简/繁、粤语、日语、韩语、英语等）。界面只显示语言的简称，不加说明文字。
  - 语言存在笔记上（`locale` 字段）。
  - 该语言的模型还没下载时，照样马上开始录音；模型在后台下载（用系统的 `AssetInventory` 流程），下载好后再识别已录的段。没网又没模型时，录音先存着，等有网再补。
  - 夹在句子里的外语词（地名、人名）会认错，靠提取时大模型结合上下文纠正、导入前地点联想确认。
- 识别和上传互不依赖：没网也能识别；识别失败的段可以重试，录音不受影响。
- 设备不支持 `SpeechTranscriber` 时（例如部分老机型），笔记照样录、照样上传，文字稿为空并标出「无法识别」，等以后的云端识别。

### 录音存储（GCS）

- bucket：`australia-southeast1`，私有，不公开访问。对象路径：`notes/{ownerId}/{noteId}/{segmentIndex}.m4a`。
- 上传：手机向后端请求**签名的可续传上传地址**（GCS resumable upload），然后直接把文件传给 GCS。断网后按 GCS 的续传协议接着传。上传成功后手机通知后端，后端校验对象确实存在再标记该段已上传。
- 播放：后端签发短时效的**签名读取地址**，手机直接从 GCS 播放。
- 手机上的本地文件在确认上传成功后才可以删除（具体何时清理见「留给实现者」）。
- 删除笔记时，后端同时删除 GCS 上的对象。
- Cloud Run 的服务账号需要 bucket 的读写权限，以及为自己签名的权限（签名 URL 用）。`scripts/deploy-api.sh` 要补上创建 bucket 和授权这一步。

### 提取（后端 + Vertex AI）

- 接口：对一条笔记发起提取，**同步**返回任务链草稿并存进 `extraction`。再次提取会覆盖上一次未导入的草稿（已导入的步保留导入记录）。
- 大模型在 Vertex AI 上调用（同一个 GCP 项目、尽量同一区域），具体选 Gemini 还是 Claude 由实现者比较后决定（见「留给实现者」），但要求：
  - 用结构化输出（JSON schema）约束返回形状；
  - 每一步必须带 `quote` 时间戳，指回文字稿；
  - 不编造录音里没有的步骤。
- 文字稿过长、超出模型一次能处理的范围时，按时间分块提取再合并。
- **控制花费**（已确认）：
  - 文字稿没变时不重复调用模型（按文字稿的哈希判断），直接返回上次的结果。
  - 每条笔记的提取次数有上限，每月总调用量有预算上限；超出时返回明确的错误，界面上按钮变为不可用。具体数值写在配置里。
- **地区**（已确认）：悉尼区域没有合适的模型时，可以调用其他区域（如新加坡、美国）。只发送文字稿。
- 提取出的 `place` 只是文字。导入前在 iOS 上用现有的地点联想（`PlaceSearch`）把它解析成名称、地址、坐标；解析不到就保持「未定位」，不阻止导入。

### 导入

- 用户在笔记详情里看到任务链草稿，可以：删掉整条链或其中某步、改名、调整步骤顺序。
- **编辑存在服务端**（设计者的决定）：每次修改都写回 `extraction`（带版本号做乐观锁，和 `children_version` 同样的做法），App 被杀后编辑还在。导入请求只带「笔记 id + 目标父任务 + 选中的链/步 id + 各步解析好的地点」，名称和顺序以服务端存的草稿为准。
- **重新提取**（设计者的决定）：已导入的步从草稿里移到笔记的「已导入」列表（记录链名、步名、导入到的任务 id），不依赖草稿 id；重新提取只替换未导入的草稿。
- 选择目标：先选 Project，再进到要放的那一级（复用 Project 列表和规划页的层级导航，以「选这里」结束）。
- 后端提供一个导入接口：给定笔记、目标父任务、要导入的链和步，**在一个事务里**：
  - 整条链（≥2 步）：在目标那一级末尾新建一个任务（链名），再按顺序给它建子任务；
  - 只选 1 步，或链本身只有 1 步：直接在目标那一级末尾建一个任务；
  - 选了某条链中的部分步（≥2 步）：仍包成一个以链名命名的新任务；
  - 写入笔记里这些步的导入状态。
- 复用现有 `createTask` 的逻辑（锁父任务、`children_version` 加一、按位置追加），不另写一套。

### 接口（新增，名称供参考）

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/notes` | 笔记列表（新的在前） |
| `POST` | `/notes` | 新建笔记（id 由手机生成，幂等；可能在录完很久后才同步） |
| `GET` | `/notes/{id}` | 详情：文字稿、提取结果、各段上传状态 |
| `PATCH` | `/notes/{id}` | 改标题、写入/替换文字稿、更新时长 |
| `DELETE` | `/notes/{id}` | 删除笔记和 GCS 上的录音 |
| `POST` | `/notes/{id}/segments/{index}/upload` | 签发该段的可续传上传地址 |
| `POST` | `/notes/{id}/segments/{index}/complete` | 手机报告该段上传完成，后端校验 |
| `GET` | `/notes/{id}/audio` | 签发各段的短时效读取地址 |
| `POST` | `/notes/{id}/extract` | 提取任务链（同步） |
| `POST` | `/notes/{id}/import` | 导入选中的链/步到某个父任务 |

### 入口

- App 里新增「笔记」入口，和 Project 列表并列（具体位置和样式在画布上定）。
- 「新建笔记」= 开始录音，一步到位。

## 与其他进行中工作的关系（设计者的决定）

- 部署脚本、API token 鉴权、Cloud Run 配置目前在 `Backendhost-2` 工作区里，尚未合并；任务耗时/花费在 `task-time-cost` 分支。写计划时以当时的 `main` 为准；这两项如果已合并，就在它们之上扩展（迁移编号顺延、导入时新任务的耗时/花费留空）；没合并，就只做不依赖它们的部分，bucket 和授权单独写成一个脚本，合并后再并入 `deploy-api.sh`。

## 留给实现者

- **大模型选择**：在 Vertex AI 上比较 Gemini 和 Claude 的中文提取质量、长上下文、价格和悉尼区域可用性后选定，结果写进 `docs/decisions.md`。
- 切段时长、音频码率。
- `SpeechTranscriber` 的具体用法（逐段文件识别 vs. 一路流式），以选能稳定处理长录音的那种为准。
- 本地录音文件的清理时机（上传确认后立即删 / 保留一段时间以便离线重听）。
- 所有步都导入后笔记是否自动归档，或只是标记为已处理。
- 签名 URL 的有效期。
- 提取的分块大小和合并策略。
- 存储和大模型的本地替身（测试用 PGlite + 内存存储 + 假模型），以及 iOS 的 `InMemoryBackend` 对应实现。

## 需要真机确认

- 1–2 小时录音在后台的稳定性、耗电和发热。
- `SpeechTranscriber` 在中文长录音上的准确度；在哪些机型上不可用。
- 模拟器跑不了 `SpeechTranscriber`，UI 测试需要用假识别器。
